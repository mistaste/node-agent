# Poland transport handover canary

Observed on iPhone build 250: fresh Wi-Fi connection passes DNS/egress and
Speedtest (222 Mbit/s). A physical network change produces repeated
CONNECTED -> TCP socket error -> WAITING_RECOVERY cycles every ~1.2 seconds.
TCP resets were observed on the endpoint's loopback listener at the same time.

The endpoint had eight established H2 transports and a per-credential limit of
eight. TrustTunnelClient's default pool itself contains eight transports; all
devices of an account share credentials. TCP keepalive used Linux defaults
(7200 s idle, 75 s interval, nine probes). HAProxy keeps the loopback leg alive
while an unreachable physical client is retained, so endpoint keepalive alone
cannot reclaim it. This is a confirmed configuration defect; validate that it
explains the field failure with repeated handover, not just an endpoint restart.

Changes:
- Finite per-account H2/H3 limit 96: five devices x eight transports x two
  generations = 80, plus 16 recovery slots. This does not alter product device
  limits or subscription enforcement.
- HAProxy frontend TCP keepalive: idle 15 s, interval 5 s, three probes.
- Frontend TCP_USER_TIMEOUT 30 s also bounds unacknowledged data; long healthy
  idle sessions retain their existing 24-hour application idle allowance.
- No global kernel sysctl change; Caddy configuration is unchanged.

Verification: full Go suite and race tests for both affected packages. Validate
the generated configuration using the installed HAProxy binary before rollout.
Canary Poland only, preserve the old image and private rendered/state files.
Field acceptance requires fresh Wi-Fi plus repeated Wi-Fi/cellular handovers,
successful data transfer, and reclamation of abandoned sockets. Other nodes
must not be claimed fixed before a separate rollout.

Sources: TrustTunnel v1.0.33 lib/src/tunnel.rs (limiter acquired on the first
authenticated request), core.rs (default TCP keepalive); pinned client
be6596652 core/src/upstream_multiplexer.h (pool size eight).
